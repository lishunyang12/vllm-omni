CORRECTION: the earlier #594 attention-kernel attribution was confounded
2026-11-18, controlled pooling follow-up

The previous warning is superseded by controlled evidence. We retract the
claim that the old 8193-token comparison established an attention regression
in #594. Native and pointer-reference preprocessing both reduced BF16 values
without explicit promotion. Installed Triton TTIR contains bf16 tt.reduce /
arith.addf; 4- and 8-warp reduction trees produce different pooled KC/VC values.
The independently autotuned pointer oracle shared this upstream issue.
Different pooled inputs alter thresholds and discrete exact/approx routing.
CuTe cache aliasing has NOT been established as the cause.

Controls and results:
* Forced old pooling configs: four token sizes, 4/8 warps x stages1..4. At8193,
  KC differed from Float64-then-BF16 reference in10535/10541 elements (4/8warps).
  Mismatches include complete blocks, not only a partial final tile.
* Freeze exactly the same native KC/VC/threshold tensors: #593 and #594 produce
  identical output SHA256 5b21c4ec0967384ec591f7209dd634959ee57ec5dd55205624032d4d9085db56
  on the original8193-token counterexample. No attention source change.
* Minimal repair: explicitly promote inputs of all four native/pointer pooling
  sums to FP32. Outputs remain BF16; API, autotune configs and attention math
  remain unchanged.
* 32 forced native config cases after repair: zero KC/VC-sum mismatches against
  Float64-then-BF16 reference. All configs agree for each tested input.
* New pooling pytest:12passed, every production config forced twice, full/tail,
  multiple batches/heads, immutable inputs and pointer padding sentinels.
* #593+same repair vs #594+same repair:29 independent-process cases, all input,
  prepared KC/VC/threshold and output hashes equal, including8 graph updates.
* Full attention validation:73/73passed, including existing oracle tolerances,
  tails, masks, long shapes and CUDA-graph input/mask mutation checks.

These are bounded numerical/correctness tests, not an end-to-end video quality
claim. No SSIM/PSNR/LPIPS or video generation was done in this follow-up.
