Findings:
SM100 power/clock confounding is resolved for the controlled measurements.
The site explicitly delegates nvidia-smi clock management. Only the two
allocated GPUs were locked. Both ran at exactly 600 or 750 MHz in measured
telemetry polls, with no software power-cap or thermal-throttle flags.
The default and firmware maximum power cap is already 1200 W; it was not raised.
Clock locks were reset after each run and restoration logs are included.
Telemetry is sampled: 600 MHz maximum gaps are below 0.66 s; the 750 MHz
diagnostic includes gaps up to 3.58 s, exposed in per-window coverage.
At matched clocks SOL is about 22% slower than Dense, consistently across
two fresh 600 MHz processes and a separate 750 MHz process. Default-node
gains of roughly 4%-7% must not be described as equal-clock kernel speedups.
Underclocking is a diagnostic control, not a production speed optimization.

The 750 MHz post-measurement profile localizes the difference to attention:
50 Dense kernels total 6.493 / 6.494 s on ranks 0/1; 50 SOL kernels total
8.372 / 8.343 s. The major GEMM totals are nearly unchanged. NCCL is much
more balanced than in the earlier default-clock profile. Diagnostic kernel
activity sums can overlap and are not substituted for measured wall latency.

SM103 was missing from the pinned upstream CuTe architecture map and launch
branch. The patch maps (10,3) to the existing SM100 kernel family in both
places. No Omni native/provider flag, BSA adapter or threshold change is added.
CuTe reduces SOL latency versus the old Triton path on B300A and GB300,
but both SOL implementations remain slower than their matching Dense baseline.
GB300 CuTe results are reproduced in two independent processes, with
byte-identical per-implementation outputs across those processes. Default
GB300 is also power-capped: Dense median clocks are about 1.54 GHz versus
SOL 2.07 GHz. The requested and maximum power limit is already 1400 W.
At 1200 MHz GB300 measures Dense 4.949 s versus SOL 6.723 s (35.8% slower).
All measured clock polls are 1200 MHz with no power/thermal flags; clocks
were reset afterward. Outputs match default-clock runs byte-for-byte. This
clock-controlled run also favors Dense; the matched
clock result does not establish a native SOL speedup over Dense. Inspect
the raw timing and sampled telemetry for that separate operating point.

B300A qualification: the cluster labels this B300A/GB112, but the driver
reports NVIDIA Graphics Device, SM103, ~139 GiB and a 600 W maximum cap.
It is an engineering device, not a production full B300 or GB300 result.
Default B300A measurements include power caps and some Dense thermal flags.
One telemetry query timed out during CuTe startup; resumed samples and the
original exception are preserved. The first of nine measured CuTe SOL
windows has no telemetry; all nine latency samples remain recorded. Clock
summaries include per-window poll counts and maximum gaps. B300A results
are exploratory and node-condition-qualified, not equal-clock comparisons.

Comparability and output limits:
GB200/GB300 use Ulysses2; B300A uses one GPU with equal CPU offload for both
variants. Weights are resident inside each measured forward. Do not compare
these products as an architecture ranking. Encoder values can differ across
hardware; identical within-node DiT inputs are replayed for each pair.
SM100 inputs and each implementation's outputs are byte-identical across
default clocks, both 600 MHz runs, and 750 MHz. Output comparison JSON also
records per-run first/last stability and SM103 Triton/CuTe tensor differences.
No decoded videos, SSIM, PSNR, LPIPS, HTTP or end-to-end quality claim is made.
